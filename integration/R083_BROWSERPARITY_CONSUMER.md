# R083 — Source-first BrowserParity consumer composition of existing Evidence Service contracts

**Why this is here:** BrowserParity-private #3 and #56 need a trusted authorization and signed evidence boundary. Existing standalone public Evidence Service already has battle-tested RDT&E primitives for source-only Ed25519 signatures (`pkg/attestation`), separately supplied grant authorization (`pkg/admission`), nonprivileged metadata/proposal operations (`pkg/controller`), and owner-private idempotent replay-*proposal* queue (`pkg/proposalstore`). We deliberately test **composition of those existing libraries**, without creating another signer, broker, policy FSM, vault or promotion API.

The `integration/browserparity_consumer_test.go` test builds an **owned synthetic** BrowserParity-shaped canonical JSON envelope with session, selected tab, generation, origin, realm, catalog, request and content hash. It signs bytes with an ephemeral Ed25519 fixture key and verifies against a separately supplied public key. The test consumer refuses wrong signer, changed bytes, ambiguous/duplicate JSON fields and **even a newly valid signature** when the envelope mismatches the independently expected tab/generation/request/realm/catalog/artifact. Positive metadata inspection and replay-*proposal* eligibility across human/AT, automation and agent projections use the existing admission engine; permission is still explicitly determined by an independently provided in-memory *fixture* grant store (no production issuer). Expired/revoked/absent grants or unauthenticated/foreign principals fail closed. The real existing `proposalstore` writes one owner-private proposal record; exact retries return the same proposal, and revocation prevents even a repeated request. No replay is executed.

**Critical negative design result:** The shared `admission.Engine.Decide` interface only binds subject, session, operation, time and grant; it has **no tab, browser generation, realm, catalog or request parameter**. Consequently, it cannot by itself qualify BrowserParity's #3 exact selected-tab operation policy. This fixture makes that difference executable: a foreign-tab or old-generation payload with a *valid* synthetic signature and otherwise approved session grant **must still be denied by the consumer's separately trusted exact scope**. The fixture's expected scope is supplied by test code, **not** a real operator or cross-process trusted source. Production must source that expected scope from the independently verified #81/#1/#2/#3 lifecycle and use evidence-service key custody and governance #56; do not copy the test's in-memory issuer.

Two independent free public Ubuntu x64/ARM64 GHA jobs run the Go integration tests with race detector, vet and source formatting; no private repository checkout, private Actions minutes, live browser, user data, credential, KMS or trusted HIL. This does not qualify `BrowserParity-private#109` G1/G2/G3, the evidence-service production signer/receiver or a physical host.

**DLE authority:** Existing `SemperSupra/evidence-service#1` retains shared primitive ownership; `SemperSupra/BrowserParity-private#3`, `#56`, `#76`, `#109` retain production authorization, custody, architecture and MVP. Keep research PR draft/non-promoting and reconcile exact red/green source and GHA evidence to the owner issues. Close evidence-only work unmerged after terminal receipts; no new production code paths.
